0TL;DR

What is it

Onboarding-as-a-product for AI-driven delivery.

Connect Git + an AI provider + a tracker; specd generates the knowledge/ wiki, AGENTS.md/CLAUDE.md rules, and spec templates as reviewable setup PRs — then runs the ticket → spec → human gate → agent → PR loop for you.

Why us

We didn't design this on a whiteboard — we operate it.

Curated repo wikis feeding a KB, knowledge-first agent rules, spec tickets with a human approval gate, as-built specs committed back to the repo, spend caps, nightly evals: all running today in a real client program. specd is that playbook with a wizard on top.

The wedge

Kiro/spec-kit give you spec files. Nobody sells the setup.

Competitors assume the knowledge base, the agent rules, and the team workflow already exist. The painful part — bootstrapping them across many repos and keeping them alive — is exactly what specd automates. VCS-agnostic, provider-agnostic, team-level.

MVP cut

Landing + wizard + GitHub + BYO Anthropic key + built-in board.

P1 in ~8 weeks: onboarding agent opens setup PRs, SpecAgent drafts Requirements/Design/Tasks, human approves, handoff to any coding agent via specd spec pull. Jira, GitLab, hosted build-runners and self-host follow (§14).

1The product in one picture

Five verbs, one loop. Everything in the UI hangs off this: Connect your tools, let specd Ground a knowledge base, Spec each ticket against it, Build behind a human gate, and Learn — the merged work updates the knowledge that grounds the next spec.

The one rule the whole product enforces Agents never implement from a bare prompt. They read the project's knowledge/ base first, work from a human-approved spec, and write what they built back into the knowledge base in the same PR. specd's job is to make installing and keeping that rule effortless — the rule itself is the product.

AGENTS.md — the rules block (core, verbatim)

# Working agreements for AI agents (generated by specd, v1 — edit freely)

## Knowledge first — no exceptions
1. Before implementing ANYTHING, read knowledge/README.md and the docs it
   maps to your task. Do not re-derive what is already written down.
2. Ground design choices in knowledge/ and cite the file you relied on
   in the PR description (e.g. "per knowledge/architecture.md#auth").
3. Update knowledge/ IN THE SAME PR as the code it describes.
   Docs ride the change; they never trail it.
4. knowledge/specs/ is a historical record (as-built). Never rewrite old
   specs; append a "Deviations" section if reality diverged.

## Spec-driven workflow
5. Work items arrive as approved specs (Requirements / Design / Tasks)
   from specd — fetch with: specd spec pull <id>
6. Implement tasks in order; one task ≤ one PR; reference the spec id
   in every branch (spec/<id>-<slug>) and PR title.
7. The final task of every spec: commit the as-built spec to
   knowledge/specs/<id>-<slug>.md in this repo's PR.

Why this file is the product's soul Requirement 6 asked for "automatic CLAUDE.md/AGENTS.md like ePD Hub": rules 1–4 are exactly the ePD operating model (knowledge-first, docs-ride-the-MR, as-built specs — their D7). Everything else specd does exists to make these seven lines true in practice: the wizard installs them, the board enforces the gate in rule 5, webhooks verify rule 7, the dashboard shows where they're rotting.

Spec anatomy (unchanged from the proven design)

Three sections per spec, Kiro-derived, team-gated: Requirements — user stories with EARS acceptance criteria ("WHEN … THE SYSTEM SHALL …"); Design — grounded in knowledge/ with per-claim citations, UNVERIFIED where it couldn't be; Tasks — ordered, each ≤ 1 PR, grouped per repo, last task always "commit this spec as-built". One approval gate for the whole spec (not three Kiro-style phase gates) — a person flips Approved; agents never approve their own input. Lifecycle: draft → in_review → changes_requested → approved → building → delivered (+ blocked for open business questions).

9Architecture

Boring on purpose: one web app, one API, Postgres, a job queue, and isolated runner containers. The only interesting decisions are the runner split (hosted vs self-hosted) and keeping git as the source of truth for knowledge.

Stack choices (recommendation, not yet a decision)

  • Frontend Next.js + TypeScript — landing (SSG, SEO for the template gallery) and app in one codebase.
  • API NestJS — team knows it cold from ePD; REST + SSE (run logs, board live-updates); WebSocket unnecessary at MVP.
  • Data Postgres + pgvector (one store for tenancy + KB index at MVP scale) · Redis/BullMQ · S3 for logs/artifacts.
  • Agent runtime Claude Agent SDK inside ephemeral containers (Fargate or Fly machines); one container per run; repo clone + scoped short-lived VCS token; egress allowlist (VCS host + LLM API only); logs streamed, then archived with secret-redaction.
  • Self-hosted runner single docker image, outbound-only job polling (GitLab-runner model) — this is what makes "subscription mode" and private-network Git legitimate and safe: credentials never leave the customer's machine (D1/D2).
As-built (rev 28) — the recommendation became code, with four deltas Shipped: Next.js 15 App Router + React 19 (10 routes) · NestJS 11, single module, ~63 REST routes + SSE across 9 controllers · Postgres 17 + pgvector via Drizzle ORM with hand-written SQL migrations (16 domain tables) · retrieval is hybrid — pgvector + tsvector fused with RRF, hash embedder by default, Voyage optional · agent runtime is the Messages API or ClaudeCodeProvider shelling out to a local claude CLI (subscription mode, D2) · self-hosted runner shipped as a Node daemon (@specd/runner): pair → heartbeat → atomic claim → report, spec/onboard jobs (build deferred, ADR 0005). 12Security & tenancy — the questions every eval asks

  • Credential vault: per-tenant envelope encryption (KMS); tokens decrypted only inside the run that needs them; never logged; runner receives short-lived scoped tokens, not the stored secret.
  • Runner isolation: one ephemeral container per run, no cross-tenant reuse, egress allowlist (VCS host + model API only), CPU/mem/time limits, workspace destroyed after log archival.
  • Code retention: hosted runners clone shallow, work, delete. The platform database stores derived data only: knowledge index (embeddings + doc text of files the customer chose to index), specs, run logs (secret-scanned). Self-hosted runners: code never touches our cloud at all.
  • Human gate as security boundary: build runs execute only against approved specs; approval is a recorded human act. Prompt-injection via ticket text therefore can't directly reach a code-writing agent — it has to survive a human review first. (Spec drafts still sanitize/flag suspicious instructions in ticket bodies.)
  • Spend: caps default-on per project; hosted runs pre-checked against remaining budget; kill-switch per project.
  • Audit: every AgentRun immutable (who triggered, model, tokens, diff links); spec approvals pinned to user+version+time.

03 · THE AGENT

An agent briefed like a senior hire — not a stranger with autocomplete

Every project gets a custom agent whose first duty is reading. The setup builds it a curated, versioned knowledge base — architecture, conventions, glossary, decisions, and every spec ever delivered — and installs working agreements that make reading, citing and maintaining that knowledge non-negotiable.

A generic coding agent

  • Rediscovers your architecture every session — expensively, from raw code
  • Invents conventions with confidence; drifts from the ones you have
  • Ships assumptions silently — you find them in review, or in production
  • Its context evaporates when the session ends
  • Output quality depends on each developer's prompt, each day

Your specd agent

  • Reads knowledge/ first — architecture, conventions, glossary, ADRs, past as-built specs. Rule 1 of its AGENTS.md
  • Works only from a human-approved spec with testable EARS criteria
  • Cites the doc behind every design claim; what it can't ground is flagged UNVERIFIED, never hidden
  • Files what it built back to knowledge/specs/ — context compounds instead of evaporating
  • Same full briefing on every run, for every developer
Full context is not a longer prompt. It's a curated knowledge base the agent must read, cite and maintain — versioned in your git, indexed by specd, enforced by the working agreements the setup installs. That's what turns a language model into your engineer.
