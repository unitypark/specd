specd · engine research № 3 · improvements plan

The engine is built. Semantica shows where to open it.

A benchmarking read of semantica-agi/semantica — a graph-native context and decision layer for AI agents — against the product specd is after two research rounds. The verdict: semantica competes on a different axis and loses to specd on truth, but it is decisively ahead on the two things this plan takes from it — a live agent-facing surface, and a knowledge lifecycle that treats records as something you query, not something you file.

Two ADRs came out of it — 0017 the engine over MCP and 0018 the working agreements as a plugin — plus the citation-judging move into packages/shared and two migrations (0017_knowledge_index_runs, 0018_gate_policy). The API suite went from 382 to 443 tests.

Three items changed shape under review, and the reasons are the useful part. Precedent retrieval did not work at all on its only production call path — the lexical predicate ANDed every term of a whole ticket — and every test passed because every test passed a tidy phrase rather than the query the caller actually sends. verify_citation was reporting specd's own indexed source files as fabricated, which is precisely the failure the four-verdict design exists to prevent. And pnpm demo ships no Dockerfile: deploy.md says no platform or image has been chosen, and answering that question sideways would have made the document wrong.

The short version (as written)

Three benchmarks now, one repeated finding. specd built a citation-grade retrieval engine — three bounded stages, provenance on every expansion, verdicts on every claim — and then gave agents a static markdown file and one CLI verb to reach it. Every benchmarked project that targets coding assistants ships a live protocol surface instead: graphify (№ 1) had an MCP server, blocking hooks and a skill; semantica productizes the same idea further — 17 MCP tools, 4 ambient resources, config for 7 editors, 17 packaged skills, 3 agent personas, and hooks that enforce rather than suggest. That is no longer a data point; it is the category's answer. Phase 1 opens specd's engine the same way — read-only, so the CLI's fetch-and-report discipline and the human gate survive intact.

The second finding is about what happens after records are written. specd's records are better than semantica's — an approved spec carries a named human approver enforced by a SQL constraint, cited evidence with four verdicts, and an as-built history with deviations. Semantica's floats and self-recorded decisions can't compete on truth. But semantica builds intelligence on top of its weaker records — precedent search, causal chains, change diffs, policy checks with recorded exceptions — while specd's stronger ones sit inert in knowledge/specs/. Phase 2 is that intelligence, rebuilt on specd's substrate, where git and Postgres already hold every input.

The third is adoption mechanics. Semantica's funnel is pip install → five-minute quickstart → doctor when something breaks. specd's is clone, env vars, compose, wizard — and deploy.md honestly reports "no host". Phase 3 is the funnel work, plus closing the gap between what the pricing page sells and what exists. What this plan deliberately does not do: chase semantica's breadth. 22 command groups, ~10 graph backends, ~11 LLM providers and an ontology stack is their maintenance bill, not our roadmap.

Section 2

What semantica is, and what it settles

Self-hosted "context infrastructure" for AI agents — ingest documents, extract a knowledge graph with LLMs, record agent decisions as graph objects, and audit everything. Aimed at regulated domains; "the open source Palantir for AI agents".

6.5k ★ · 681 forks
MIT, Python, active Discord + Discussions; issue refs reach #928, and v0.6.5 is a security release
~179k LOC · 267 test files
349 engine files under semantica/; a single 4,400-line click CLI with 22 command groups
17 tools · 4 resources
modular MCP server, stdio JSON-RPC, ready configs for Claude Code, Cursor, Windsurf, Cline, Continue, VS Code, Amazon Q
17 skills · 3 agents · hooks
one shared plugin body shipped under 8 per-editor manifests, installable as an in-repo Claude Code marketplace

It is not a competitor on specd's axis. Nothing in it produces specs, enforces a human gate, reads a repository, or measures docs against code. Its truth model — LLM-extracted facts with confidence floats, validity windows instead of verification — is exactly what specd's four-verdict, no-LLM-at-index design refuses to be. Where it overlaps specd is the knowledge-for-agents layer, and there it settles four questions:

  • How do agents reach a knowledge engine? Through a live protocol surface — tools for queries, resources for ambient state — not through prose exported at onboarding time. Third benchmark, same answer.
  • How do working agreements ship? As installable skills, hooks and agent personas versioned in the repo. Semantica's PostToolUse hook AST-parses every file the assistant edits; its skills are sub-commanded runbooks; its kg-assistant agent is an API-signature reference as a persona. Rules that matter run as code.
  • What are decision records for? Querying. find_precedents() ranks similar past decisions (hybrid semantic + graph proximity) before an agent acts; causal links make chains traversable; policy checks record exceptions with an approver and a justification, never silently.
  • What is a knowledge change? An event with a diff. Snapshots, compare_versions(), checksums, per-node history — machinery semantica had to build because it has no git underneath. specd has git underneath. It shows nothing.

Section 3

The target surface: one engine, four doors

Nothing new is built inside the engine this round. Every addition is a door onto what rounds № 1–2 already built — and every door is read-only or gate-checked, so the CLI's discipline ("fetches, registers and reports; never authors, reviews or approves") extends unchanged to every agent.

A stdio MCP server as a new CLI subcommand — Go, in the existing binary, a thin client over the HTTP API using the keychain token, exactly as every other CLI verb works. shipped #94 1.2 — A Claude Code plugin: AGENTS.md rules become executable

semimpact: higheffort: M

Semantica ships one plugin body — skills, agents, hooks — under eight editor manifests, and makes its own repo an installable marketplace (marketplace.json). specd's version writes itself: AGENTS.md’s rules are currently enforced by hope past the three specd already binds in software. As a plugin: /specd:pull (fetch, verify buildable, set up the spec/<id>-<slug> branch), /specd:implement (task loop, one commit per task, verify command between tasks), /specd:as-built (render the deviations section against the pulled spec). Phase 2

Records become intelligence

semantica's lifecycle, specd's substrate

shipped #97 2.1 — Precedents: as-builts and ADRs answer before drafting starts

semimpact: higheffort: M

Semantica's best verb is find_precedents() — ranked similar past decisions, consulted before acting, with the docs' own caveat kept: precedents guide, they don't determine. specd already owns richer precedents (as-built specs carry outcomes, deviations and verify results; ADRs carry rationale) and already has the retrieval machinery — the gap is a lens. Give spec and adr docs a precedent-scoped retrieval mode; put a "Precedents" section in the SpecAgent's context (id, title, outcome, deviation count, verify result — citable like any other evidence); show the same list in the SpecDrawer so the reviewer sees what history says before approving. No confidence floats — ranked RRF scores with the ranking reason shown, consistent with house honesty rules.

shipped #101 2.2 — The index-run digest: what changed in what we know

semimpact: med-higheffort: S-M

Semantica snapshots whole graphs into SQLite with checksums to be able to say "nodes added, edges removed, here's the diff" — machinery it needs because it has no git. specd's index run already computes every input inside its transaction: docs added/changed/removed, links resolved and broken, health before and after. It records none of it. Persist a per-run summary row and surface it — in the reindex response, in KnowledgeView as "last index run", and on merge in the run history. The reviewer question it answers is semantica's best product surface, free on our substrate: what did this merge change in what we know?

shipped #102 2.3 — Re-verify citations where the gate is re-checked

semauditimpact: higheffort: S-M

Semantica's temporal-validity instinct — a fact is valid for a window, and queries must not serve expired facts — applied at specd's most important moment. A spec approved Monday can build Friday against knowledge that merged Wednesday. The build station already re-checks approval at the point of use; extend the same re-check to re-run claim verdicts against the current index and carry "N citations stale since approval" into the run log and the PR body. shipped #103 2.4 — Policy as data on the gate, with exceptions that leave a trace

semimpact: medeffort: M

The gate is binary today; projects will want house rules — and semantica's PolicyEngine has the one detail worth stealing whole: non-compliance can be recorded as an exception with an approver and a justification, never silently. Section 5

Do not adopt

  • LLM extraction at index time, confidence floats on facts. Semantica's truth model is extracted facts scored 0–1 by the extractor. specd's is cited claims judged supported / stale / unsupported / unknown by a deterministic validator. Verdicts are evidence states; floats are vibes. This is the moat — round № 2 made it, this round keeps it.
  • Whole-graph snapshots, checksums, rollback, per-node history. That subsystem is git rebuilt for products without git underneath. specd's knowledge is files in the user's repo; its index is derived and rebuildable by design. Take the digest (2.2), not the machinery.
  • The ontology stack and polyglot backends. OWL, SHACL, SKOS, ~10 graph stores, ~7 vector stores, ~11 LLM providers. ADR 0008 removed Redis for less. One Postgres and one provider is not a limitation to apologize for; it is why sixteen migrations and two CI commands cover the whole product.
  • An authoring CLI. Semantica's CLI does everything; specd's deliberately cannot author, review or approve — that asymmetry is what makes the gate credible, and 1.1 extends it to MCP rather than weakening it.
  • Runtime agent-memory tiers. Conversation namespaces, retention windows and ring buffers solve long-running chat agents. specd's agents are bounded runs against a worktree whose memory is the spec, the commits and the as-built. Different problem, correctly not shared.

Deferred, not rejected

  • A knowledge-graph explorer UI. Semantica's Sigma.js explorer is its demo centerpiece, but KnowledgeView already answers the questions people actually ask. The specd-shaped first step, when MCP consumers start asking for paths: a one-hop citation mini-graph in the SpecDrawer, showing a claim's evidence neighborhood at review time.
  • Conflict detection between docs. Semantica flags contradictory facts before merge — with an LLM. A deterministic sibling (two docs claiming the same glossary term or symbol with diverging freshness) may earn a place as a health signal; anything model-driven at index time stays out.
