What specd should take from code-graph-rag — and what it should fix first

A benchmarking read of vitali87/code-graph-rag against a file-level audit of specd's knowledge engine as built. The verdict: code-graph-rag validates every architectural bet specd has made, contributes four ideas worth adopting outright, and hands us the blueprint — and the cost ceiling — for the one strategic feature specd is missing: a code-aware knowledge graph.

The short version (as written)

specd's core bets are right, and code-graph-rag proves it at scale. Deterministic indexing with the LLM only at the query boundary, Postgres as the only store, deterministic fusion instead of model-driven retrieval — cgr validates the first at 14-language scale and involuntarily proves the second two by counterexample (its graph DB timed out at 101k edges and its own analyses now bypass it).

But the audit found real correctness debt to clear first. No transaction wraps any index write, the shrink guard checks volume rather than provenance, the truncation notice cries wolf on nearly every draft, and the graph S-102 built is starved — the onboarding template generates zero extractable links and code paths are excluded by regex.

The plan is three phases: repair the foundations (1–2 weeks of PRs), sharpen the citation discipline that is specd's moat (cgr has nothing like it), then build code-awareness as a symbol index, not a call graph — cgr's own evidence says the symbol layer is ~1,600 lines and scores perfectly against independent oracles, while the call graph is where 14,000 lines and the maintenance nightmare live.

Part 1 · The audit

Where specd stands after S-102

The engine (~1,400 lines in apps/api/src/knowledge/) is disciplined where it matters most: extraction is deterministic with no model calls, edge replacement is tier-scoped per doc, citation validation covers graph-expanded chunks, and hub gating plus a strict expansion budget keep retrieval bounded. That's the right skeleton. The audit found six defects worth naming — three are broken promises from S-102, three are quiet design flaws.

Part 2 · The benchmark

What code-graph-rag is, and what it settles

A solo-maintained, MIT-licensed CLI + MCP server that tree-sitter-parses a polyglot monorepo into a Memgraph property graph, then lets an LLM write Cypher against it — with optional code editing. Pre-1.0 with a patch release per merge, unusually serious about testing, unusually raw at the architectural seams.

77.7k / 254k
production vs test LOC — a 3.3 : 1 test ratio, the repo's most credible quality signal
14 + YAML tier
languages with full tree-sitter specs, plus a one-YAML-file tier for cheap new-language support
0 LLM calls
at index time — the whole semantic pipeline is deterministic, same bet as specd, at 14× the language surface
F1 0.957
retrieval vs an independent oracle on django (~2,900 files) — the most honest number; the headline "1.0" is self-scored

Three things it settles for specd

The Postgres-only constraint is an advantage, not a limitation. cgr's two most valuable analyses (dead code, flow reachability) both bypass Memgraph — they fetch the edge list into Python and BFS there, because the per-root Cypher hit the database's 600-second timeout on django (31k roots, 101k CALLS edges). The graph DB is used as an indexed edge store, which is exactly what a code_edge table with a recursive CTE does — inside a transaction, which cgr's store doesn't have at all (dead_code.py:1-7 · graph_service.py:225).

Deterministic-index / LLM-at-query-boundary scales. Nothing LLM-shaped is reachable from cgr's indexer across 14 languages of genuinely semantic extraction — call resolution, type inference, taint. The index stays reproducible, diffable, oracle-testable, and free. specd's identical bet for docs extends cleanly to code.

Deterministic fusion beats model-driven retrieval. cgr's NL→Cypher has regex-only validation and no repair loop — a wrong-but-valid query is indistinguishable from "no results". Its vector arm isn't fused with the graph arm at all; an LLM is told in prose to combine them. specd's fixed RRF + bounded expansion pipeline is the stronger design; the reliability budget belongs there, not in query generation.

And one thing specd has that cgr lacks entirely: per-claim citation validation. cgr's provenance discipline stops at "cite your sources" in a prompt (prompts.py:194). Nothing checks a citation against what was retrieved. That validator is specd's moat — Phase 2 doubles down on it.

shipped #35 1.1 — One transaction per repo index run, and the real shrink guard

S-102 debtimpact: higheffort: M

Wrap indexRepository's writes in a single transaction and implement the guard S-102 actually specified: abort when the run would remove docs or edges whose sources were neither re-indexed nor deleted in this run — a provenance check, not today's count-and-ratio heuristic. cgr is the cautionary tale here: its autocommit delete-then-reinsert incremental path can be left permanently half-deleted by one crash. Postgres gives specd the rollback for free; it's currently unused.

Concretely One db.transaction around upserts/deletes per repo; guard compares the removal set against this run's discovered-paths set; append the four unrecorded deviations to S-102's Deviations section in the same PR (repo rule 4).

knowledge.service.ts:173, :241-250, :871-886 · cgr: graph_service.py:225

shipped #36 · #37 1.2 — An extractor fingerprint as the second cache key

cgrimpact: higheffort: S

The per-doc SHA skip has a blind spot cgr names precisely: "a graph is a function of (source files, parser code, parser config)" — specd hashes only the first. Change the chunker, embedder, or link extractor and every unchanged doc keeps old-generation rows. The hand-bumped LINKS_VERSION = 2 is a special case of the general mechanism; generalize it: fingerprint chunker + embedder (provider, model, dims) + extractor versions, stamp it per index generation, force a full re-index on mismatch. This also closes A3's mixed-vector-space hole.

knowledge.service.ts:41, :106-133 · cgr: parser_fingerprint.py:15-42

shipped #36 · #37 1.3 — Make the truncation notice honest

auditimpact: higheffort: S

cgr gets one thing exactly right that specd currently gets wrong in practice: truncation must announce itself truthfully, because "the agent sees a truncated list and assumes it is complete." specd's notice fires on essentially every draft with a meaningless count (A2). Compute matchedCount from real corpus-bounded counts — the lexical arm's match count plus a similarity-thresholded dense count — so the notice appears only when relevant material was actually cut, and its number means something.

knowledge.service.ts:431-465, :491 · cgr: structural_search.py:17-21, token_utils.py:23-53

shipped #36 · #37 1.4 — Embedding provider hardening

auditimpact: medeffort: S

Three one-line bugs with outsized quiet cost: configured-Voyage-without-key silently degrades to the hash embedder; queries embed as input_type: 'document' (Voyage's asymmetric query type is never used); and no provider/dim stamp exists on chunk rows. Fail loudly on misconfiguration, use 'query' at query time, stamp provider per chunk, and refuse to search across mixed spaces (the 1.2 fingerprint enforces the rebuild).

shipped #38 1.5 — Take indexing off the webhook's back, batch the writes

auditimpact: med-higheffort: M

Indexing currently runs synchronously inside the webhook HTTP request — chunk-by-chunk INSERTs, a project doc-list load per doc, a SELECT per anchored link, an HTTP GET per file. Phase 2

Sharpen the moat: citation discipline & graph value

✓ complete — #39 · #40 · #41 · #42 · #43 · #44

shipped #40 2.1 — Three-verdict citation validation with coverage gaps

cgrimpact: highesteffort: M

The single best idea in code-graph-rag, from its flow analysis: "an absent path must never read as a PASS" — an empty result is only meaningful if you know the analysis covered the space. Ported to specd's validator: a claim's citation today resolves to valid-or-UNVERIFIED, a binary. Make it three-valued — SUPPORTED (exact chunk match, anchor-strict — closing the loose-anchor hole from A6), UNSUPPORTED (cites material that was retrievable but wasn't retrieved or doesn't exist), and UNKNOWN (the corpus couldn't answer: the doc failed to index, was truncated out, or sits orphaned off the graph). specd already computes the coverage ingredients — orphan docs, broken links, index failures; they just never reach the verdict. "No evidence found, and these 3 docs failed to index" is a categorically more useful answer than a silent UNVERIFIED.

Concretely Per-doc coverage flag set during indexing (cgr's flow_covered); validator consults it plus honest truncation (1.3); anchors validated against the retrieved chunk's real heading; verdict + reason persisted per claim, surfaced in the run log and spec review UI.

spec.agent.ts:276-328, :292 · cgr: flow_verdict.py:1-6, :50-94

shipped #44 2.5 — Git history as a signal source: co-change edges and real drift

new signalimpact: higheffort: S-M

Git is the one source specd trusts absolutely — "git is truth; the index is derived" — yet the engine only ever reads HEAD. Mine a bounded window of history (12–24 months, filtering the classic poison: lockfiles, generated paths, and bulk commits touching 100+ files) into two deterministic signals. First, per-doc commit metadata. Second — the killer app — doc↔code co-change coupling: which code paths historically change in the same commits as each doc. That turns drift detection from the current 90-day proxy into the honest claim the knowledge README already makes and can't back: "this doc's coupled code has changed 14 times since the doc was last touched." Neither benchmark can do this — code-graph-rag walks the filesystem and explicitly abandoned rename handling; graphify has no git integration at all.

Concretely Co-change lands as a new edge kind in the existing table — kind: 'cochange', origin_tier: 'history', finally using the tier seam S-102 shipped and never filled — weighted below authored links (statistical, not intentional). It runs on the runner over a real clone (one git log --numstat; the REST adapters can't crawl history within rate limits), bootstrapped at onboarding and kept fresh from webhook push payloads at O(new commits). The digest (hotspots, cadence, branch conventions) also feeds the onboarding agent's prompt so generated docs describe the living parts of the repo. Aggregate author data before anything customer-visible. This is also the prerequisite for 3.2's "changed in the same PR as the doc" edge weighting.

shipped #43 2.6 — One schema table → prompt, audit, and docs

cgrimpact: medeffort: S

cgr defines its node/edge schema once as typed tuples and generates three consumers from it: the LLM's prompt block, a structural graph audit, and the docs — so none can drift (and the one table it maintains by hand is exactly where its docs did drift). specd's link kinds, edge weights, and provenance fields should live in one constant table generating the SpecAgent's retrieval-schema prompt, an index-integrity check, and the knowledge-docs section. Also the cheapest place to unify the two slugifiers (A6) into the shared module S-102 mandated.

Phase 3

Code-aware specd — a symbol index, not a call graph

✓ complete — #46 · #47 · #48 · #49 · #50 · #54 · #58

shipped #46 · #47 3.1 — Tier-1 symbol index over the target repo

new capabilityimpact: higheffort: L

specd indexes zero source code today — the onboarding scan reads manifests only and discards even those. The strategic gap: a SpecAgent drafting a spec about RunnerJobsService cannot see that it exists, where it lives, or that an ADR's reference to it went stale two renames ago. cgr's cost accounting scopes the fix precisely: its symbol/containment layer (language specs, qualified-name registry, parser loader) is ~1,600 lines for 14 languages and scores F1 ≈ 1.0 against independent oracles — while call resolution is 14,000+ lines, a 15-pass hand-ordered pipeline, and the entire maintenance nightmare. Spec grounding needs the former, not the latter.

Concretely Tree-sitter symbol extraction for 3–5 launch languages (TS/JS, Python, Go match specd's own stack), a declarative per-language spec after cgr's LanguageSpec/FQNSpec shape. Two tables: code_node(repo, kind, qualified_name, path, span, blob_sha, commit_sha) with a unique index per (repo, kind, qualified_name) — plus a reverse(qualified_name) index from day one (suffix lookup was cgr's #1 hot path, 48% of CPU until indexed) — and code_edge for containment + imports only. Dotted qualified names with per-language file→module rules, adopted verbatim; cgr's collision-variant scheme (name@line) for legitimate duplicates.

onboarding.agent.ts:84-108 · vcs.types.ts:77-95 · cgr: language_spec.py:342-659, function_registry.py:69-90, BENCHMARK_REPORT.md:15-30

shipped #46 · #48 · #50 · #58 3.2 — Doc↔code links, and STALE as a first-class verdict

new capabilityimpact: higheffort: M

This is where specd overtakes the benchmark, because cgr has no docs layer at all. The existing knowledge_links table already carries kinds and resolution states — add code-target kinds (pathref resolving to a real file at HEAD, symbolref resolving `RunnerJobsService.claim` to a code_node). Retrieval expansion works unchanged: a chunk citing a symbol pulls the symbol's snippet with via:'graph' provenance. Edge weights become the tuning surface: a link to a symbol touched in the same PR as the doc (2.5's history signal) outweighs one to a symbol they last shared years ago. And because every code node carries its blob and commit SHA, a citation to a symbol whose blob changed since indexing becomes STALE — feeding directly into 2.1's verdicts. "This ADR references three symbols; two exist, one was deleted in commit X" becomes a health note. cgr can't say that — it re-reads disk at answer time and can silently disagree with its own index.

schema.ts:389-418 · knowledge.service.ts:503-615 · cgr: code_retrieval.py:76-104

shipped #48 (by content identity) 3.3 — Incremental by git diff, with store-rehydrated resolution

cgrimpact: higheffort: M

cgr walks the filesystem with an MD5 cache and a mtime fast path (which archive restores and rsync silently defeat), and it explicitly gave up on rename detection. specd is derived-from-git: git diff -M --name-status base..head yields the changed set with renames for free, no cache, no mtime trust. Copy the two ideas cgr got right: rehydrate the symbol table for unchanged files from Postgres before resolving links in changed ones (one indexed SELECT — otherwise a doc referencing an untouched symbol loses its edge on every merge), and its failure policy verbatim: a rehydration read failure aborts the incremental run, never silently degrades it. All inside the Phase-1 transaction, which makes cgr's fragile capture-and-restore dance unnecessary — inbound rows are never deleted in the first place.

cgr: graph_updater.py:1064-1150, :1077-1085, :1744-1748 · evals/README.md:210-218

shipped #49 · #54 3.4 — An eval harness with independent oracles

cgrimpact: medeffort: M

The strongest thing in cgr's repo is its eval discipline: per-language independent oracles (Python ast, the TS compiler API, go/parser…), a fair-file-set rule, an incremental-correctness eval whose oracle is a clean full re-index, and published corrections against itself. Its one flaw: the default target is its own codebase, where it reports a perfect 1.0. Adopt the methodology, invert the default: grade specd's link extraction and symbol resolution against independent parsers on external corpora, keep self-indexing as the smoke test. The incremental-vs-clean-rebuild eval is the one that catches the bugs that matter (cgr: only 10 of 25 edits reproduced a clean index exactly, before its eval-driven fix).

cgr: evals/README.md:153-218, :925-1043, :1101-1102 · evals/cli.py:22-24

Part 5 · Negative space

Do not adopt

Documented so the next benchmarking exercise doesn't relitigate them.

  • Memgraph — or any graph database. cgr's own scale evidence is the argument: two analyses retreated to client-side BFS after 600s timeouts at 101k edges, the store runs without transactions, unbounded in memory, three Docker containers deep. Postgres tables + recursive CTEs reproduce the model transactionally. dead_code.py:1-7 · flow_verdict.py:4-6 · docker-compose.yaml
  • NL→Cypher query generation. Regex-validated, no repair loop, and a wrong-but-valid query reads as "no results". specd has no query language to generate; keep retrieval a fixed, testable pipeline. llm.py:60-154
  • Write tools and shell access in the retrieval loop. cgr's approval machinery is genuinely well-built — and entirely unnecessary for a consumer that drafts specs. The SpecAgent should never hold a pen that edits repos. shell_command.py:69-267 · file_editor.py:302
  • Repo-supplied instructions in the system prompt. cgr concatenates the analysed repo's .cgr.md into its system prompt — a direct prompt-injection channel from a hostile repo, unacknowledged in its security docs. specd indexes third-party repos' docs; keep them in user-turn context behind untrusted-content delimiters, always. config.py:492-501 · prompts.py:200-207
  • Watch-mode style O(whole-graph) refresh. One saved file triggering a full CALLS wipe-and-recompute across every project in the store. specd's merge-driven, per-doc incremental model is already correct; extend it, never replace it. realtime_updater.py:322-323
  • mtime-trusting fast paths. Archive restores, rsync, and container copies rot the index silently. Git diff makes the entire mechanism unnecessary. graph_updater.py:1744-1748
  • Self-scored headline numbers. If specd publishes benchmarks, the external corpus is the headline and the self-test is the smoke test — cgr's committed 1.0-across-the-board on its own source is what not to do; its django 0.957 is what to publish. evals/results/scores.csv · evals/README.md:139-140
