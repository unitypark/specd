## What specd is

A monorepo implementing a spec-driven delivery pipeline: `Connect → Ground →
Spec → [human gate] → Build → Learn` (README). The station line is fixed and
only station 01 takes configuration (D11, `SPEC-PLATFORM-PLAN.html`); the
gate at 04 is structural — a state machine in
`packages/shared/src/lifecycle.ts`, not a convention.

## Workspace layout

pnpm workspace (`pnpm-workspace.yaml`) over `packages/*` and `apps/*`. The
`cli/` directory is a Go module and is **not** a pnpm workspace member — it is
driven by root scripts. `evals/` at the root is the grading harness (`pnpm
eval`), also outside the workspace on purpose: evals grade, they never gate.

| Path | Role (verified in source) |
| --- | --- |
| `apps/api` | NestJS API — auth (`src/auth/`), projects and connections, spec pipeline and agents (`src/agents/`), VCS webhooks (`src/vcs/`), knowledge engine (`src/knowledge/`) |
| `apps/web` | Next.js — landing, wizard, dashboard, board, spec review, knowledge, runs |
| `apps/runner` | Self-hosted runner daemon — claims dispatched jobs, heartbeats its lease, drives the local Claude Code CLI (`decisions/0004`, `0009`) |
| `cli` | Go `specd` binary (`cmd/specd`, `internal/{api,config}`) — thin client (D13): login, spec pull, runner pairing, the REPL |
| `packages/shared` | Spec lifecycle state machine (`lifecycle.ts`), spec content + EARS (`spec.ts`), model allowlist + rate card (`models.ts`), Claude-reply parsing and shape-check (`claude-code-parse.ts`) |
| `packages/db` | Drizzle schema (`src/schema.ts`, 20 tables) + plain-SQL migrations |
| `packages/templates` | `AGENTS.md`, `CLAUDE.md`, `knowledge/` scaffold for onboarded repos; `evidence.ts` reads a repo's facts (commands, CI, services, config, entities) before any model call (`decisions/0015`) |

File counts are deliberately not recorded here — they rot faster than roles.
Roles above were verified in source on 2026-08-11: `apps/api/src` is NestJS
modules wired in `app.module.ts`, and `packages/shared` exports exactly what
the table claims.

## Ports and entry points

API on `:4000`: `apps/api/src/main.ts` bootstraps Nest and serves under
`/api`; the port is `Config.port` (`PORT`, default 4000,
`apps/api/src/config.ts`). Web on `:3000`: `next dev -p 3000`
(`apps/web/package.json`).

## AI provider modes

Three modes (§P3). The mode is **not** an API environment variable — it lives
on the project's AI connection (`connections.settings.mode`, default
`managed_cloud`) and is resolved per run in
`apps/api/src/projects/connections.service.ts`. The `SPECD_AI_MODE` env var
exists only as the headless loop driver's knob (`apps/api/src/e2e-loop.ts`).

1. `subscription_runner` — the run is dispatched as a job that a paired
   self-hosted runner claims (`decisions/0004`, `0005`);
   `apps/runner/src/claude.ts` drives the machine's locally logged-in Claude
   Code CLI. No credential is stored or proxied; no per-call billing; no
   schema guarantee, so the reply is shape-checked against the schema's
   required keys with one lossless control-character repair before parse
   (`packages/shared/src/claude-code-parse.ts`).
2. `api_key` — Messages API with the project's vaulted key, metered per token
   from the rate card in `packages/shared/src/models.ts` (`costEurCents`,
   integer EUR cents).
3. No credential — onboarding still writes a scaffold, and since
   `decisions/0015` it is a useful one: the commands, pipelines, services,
   configuration, entities and test layout are all read out of the repo
   without a model. Only the judgement sections stay empty, each carrying the
   question it exists to answer. Other agent runs fail with a clear error
   naming the missing key rather than inventing content.

## Invariants enforced in code

Each row was verified at the named symbol on 2026-08-11.

| Invariant | Enforcement point (verified) |
| --- | --- |
| Only a named human approves | `SpecsService.transition` (`apps/api/src/specs/specs.service.ts`) refuses `approved` outright to any agent; `isHumanOnlyStatus` in `packages/shared/src/lifecycle.ts`; DB CHECK in `packages/db/migrations/0001_init.sql` — an `approved` row without approver name + timestamp cannot exist |
| Gate cannot be bypassed | `spec_not_approved` 409 raised server-side (`apps/api/src/common/errors.ts`), surfaced by the CLI (`cli/internal/api/client.go`); CLI tokens carry `aud: 'cli'` and `auth.guard.ts` rejects them on any route not explicitly marked CLI-allowed |
| Gate is closed to every board gesture | The board refuses `approved` as a drop target *and* as a keyboard move, handing back the reason rather than letting the server answer 403 (`dropCheck`, `neighbourColumn`, `apps/web/lib/board.ts`). A drop on the lane a card already occupies is ranking only, never the transition that lane's status would permit (`planDrop`) — otherwise nudging a `changes_requested` card up its own column would silently resubmit it for review |
| Approval is append-only | `TRANSITIONS` in `lifecycle.ts` has no edge from `approved` back — only `building`/`delivered`; a revision is a new version carrying `supersedes`, and v1 keeps its stamp |
| Citations are checkable | Validated against retrieved content and coverage (`apps/api/src/knowledge/`): `supported` / `unsupported` / `unknown`, plus `stale` on a second axis — the passage describes code that moved since the doc was touched. Invented docs and sections are demoted; a real doc retrieval never surfaced is reported unchecked rather than wrong (see `conventions.md#writing-conventions-the-product-itself-enforces`) |
| Loop closes | Last task of every spec files the as-built copy to `knowledge/specs/`; `apps/api/src/agents/spec.agent.ts` appends that task if the model omitted it |
| Spend capped | `SpendCapExceeded` thrown before a run starts (`apps/api/src/runs/runs.service.ts`); cost metered in integer EUR cents (`costEurCents`) |
| Agents never push | The build run allowlists editing tools only (`apps/runner/src/claude.ts`: `--allowedTools` includes `Edit`, `--permission-mode acceptEdits`); pushing is specd's own act, only ever to the spec's branch |
| Deletion cannot erase the audit trail | A ticket whose spec reached the gate refuses deletion (`ticket_has_delivered_work`, `apps/api/src/board/board.service.ts`); deletes are refused while runs execute (`runs_in_flight`); run history and webhook deliveries survive deletion with references nulled, never cascaded; project delete is owner-only and the UI demands the slug typed back |
| GitHub not impersonable | `github-webhook.verify.ts`: HMAC over raw bytes in constant time before parse, unset secret rejects all; `github-webhook.service.ts`: dedup by delivery id, repo+installation must match a project |
| GitLab not impersonable | `gitlab-webhook.verify.ts`: secret-token comparison (GitLab does not sign payloads) in constant time, unset secret rejects all; dedup by delivery id; repository match scoped to the sending instance (`project.web_url` vs. the connection's `instanceUrl`) so two instances sharing a numeric project id cannot cross-trigger each other's specs (`decisions/0002`) |

## Data model

`packages/db/src/schema.ts` defines 20 tables; migrations are plain SQL in
`packages/db/migrations/` (15 as of 2026-08-11, `0001`–`0015`), applied in
filename order. Grouped by domain:

- **Identity & access** — `users`, `memberships`, `device_codes` (CLI device
  flow), `runners` (paired machines, token hashed at rest)
- **Projects & wiring** — `projects` (`setup_completed_at` NULL = wizard
  draft: resume/discard on the dashboard, never listed as real),
  `connections` (VCS / AI / tracker, one row each), `repositories`
- **Delivery** — `tickets`, `specs` (versioned, append-only, `supersedes`),
  `spec_comments`, `agent_runs`, `run_logs`, `webhook_deliveries` (audit
  trail, pruned by age — S-103)
- **Knowledge engine** — `knowledge_docs`, `knowledge_chunks` (pgvector +
  weighted tsvector), `knowledge_doc_links` (the graph), `knowledge_health`,
  `knowledge_doc_coupling` (0013), `code_nodes` (0014), `repo_commits`
  (hosted-repo history ledger)

Read `packages/db/src/schema.ts` before assuming any column — this list names
the tables, not their shapes.

## Trust boundaries

- CLI is a thin client (D13): fetches, registers, reports; never authors,
  reviews or approves. Enforced server-side, not by CLI politeness:
  `auth.guard.ts` rejects `aud: 'cli'` tokens on every route not explicitly
  marked CLI-allowed.
- `specd login` is a device flow requiring the web app (`/cli-login`) for
  human confirmation (`apps/api/src/auth/auth.service.ts`). The token lands
  in the OS keychain (service `specd-cli`; the runner's token in its own
  account) with a `0600` file under the config dir as fallback —
  `cli/internal/config/config.go`.
- Git is the source of truth for knowledge; the platform holds only a derived
  index (embeddings, metadata, run history).
